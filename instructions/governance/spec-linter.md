# Governance: SPEC Linter

## Когда применять

- Перед approval новой SPEC и при review качества спецификации.

## MUST

- Для short SPEC проверить пять содержательных критериев из таблицы ниже с конкретным evidence или планом проверки для текущей фазы. Не оценивать отдельно 20 expanded-пунктов и не добавлять числовой rubric либо перечень неприменимых ролей.
- Для expanded SPEC оценить каждый критерий 1..20 как PASS/PARTIAL/FAIL с коротким проверяемым пояснением. Оцениваются сведения, а не число заголовков.
- Неприменимость сопровождать причиной; отсутствие критичного сведения не маскировать `Не применимо`.
- Для expanded итог ГОТОВО допускается без FAIL в A/C/D; любой FAIL A/C/D требует доработки. Для short должны быть проверены все пять содержательных критериев. Severity, disposition findings и запреты PASS определяет только `review-loops.md`; оценки linter не заменяют обязательные условия текущей фазы.
- Сохранить результат в рабочей SPEC. Для PARTIAL указать конкретный остаточный риск и действие.

## Пять проверок short SPEC

| № | Что проверяется | Достаточное содержание |
| --- | --- | --- |
| 1 | Результат / границы | Исходное поручение и наблюдаемый сценарий, проверенный AS-IS, ограниченный outcome, Non-Goals и eligibility short |
| 2 | Решения / разрешения | Выбранные решения, существенные неизвестные и уже разрешённый scope; exact approval по фазовому owner |
| 3 | AC→evidence | Обязательные AC связаны с релевантной проверкой исходного сценария; до EXEC — план, после — фактический результат |
| 4 | Существенный риск / rollback | Вероятный дефект или user objection, безопасное исправление/откат; неприменимость объяснена |
| 5 | Findings / disposition / stop | Что реально проверено, что исправлено или осталось, основание остановки по review owner |

Эти сведения могут находиться в общей таблице; повторять их в отдельных linter/review/role разделах не нужно. Компактность не отменяет применимый обязательный контракт.

## Критерии expanded SPEC

| № | Блок | Что проверяется |
| --- | --- | --- |
| 1 | A | Цель и наблюдаемый outcome |
| 2 | A | Проверенный AS-IS |
| 3 | A | Корневая проблема |
| 4 | A | Цели дизайна |
| 5 | A | Границы / Non-Goals |
| 6 | B | Ответственности |
| 7 | B | Точки интеграции |
| 8 | B | Алгоритмы и инварианты |
| 9 | B | Ошибки и recovery |
| 10 | B | Performance либо обоснованная неприменимость |
| 11 | C | Данные / состояние |
| 12 | C | Совместимость и миграция |
| 13 | C | Rollback |
| 14 | D | Измеримые AC |
| 15 | D | AC→test/evidence, включая негативные случаи |
| 16 | D | Команды и stop rules |
| 17 | E | План и зависимости |
| 18 | E | Решения и открытые вопросы |
| 19 | E | Масштаб и выбранная форма |
| 20 | F | Соответствие применимому profile |
