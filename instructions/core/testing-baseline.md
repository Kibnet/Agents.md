# Core: Testing Baseline

## Когда применять

- Для любых изменений кода, влияющих на поведение системы.
- Для исправления багов и регрессий.

## Когда не применять

- Для чисто документальных правок без изменения поведения.
- Для временных черновиков, которые не попадают в основной поток изменений.

## MUST

- До реализации определить обязательный набор проверок и объяснить его риском и областью влияния в SPEC. Сохранять явные repo/CI/release gates и обязательства уже утверждённой SPEC; обновление каталога не освобождает от них.
- Изменения поведения проверять содержательными автоматическими проверками наблюдаемого результата или контракта. При воспроизводимом баге сначала найти или добавить failing regression check, подтвердить причину, затем исправить ошибку. Если воспроизведение недоступно, зафиксировать ограничение и next-best evidence; не выдумывать RED.
- Выполнять staged validation: characterization/failing check -> targeted tests -> affected build -> остальные обязательные проверки выбранного набора. Для локального UI/copy/layout изменения с доказанно ограниченной областью влияния достаточны затронутые тесты, сборка и визуальная проверка, если отдельный применимый gate не требует большего.
- Полный набор тестов обязателен при изменениях общих storage/config/security/публичных контрактов, миграциях, широкой или неизвестной области влияния либо явном repo/CI/release gate. Малый diff сам по себе не доказывает низкий риск. Ограниченный набор требует обоснования границ влияния, а не удобства или длительности full suite.
- До длинного шага сообщать команду, repo-specific expected duration и способ получить progress/log evidence; универсальный time budget не вводить.
- После timeout не повторять идентичную команду. Сначала получить progress/root-cause evidence, изменить scope/ресурсы или устранить lock/environment blocker.
- Перед успешным завершением получать green для всего обязательного набора проверок. Authoritative CI допустим как эквивалент только если это прямо разрешает repo owner contract и итоговый статус green; `pending`, `timeout`, `cancelled` и red не являются evidence. Нельзя сокращать ранее обязательный набор после failure, чтобы объявить PASS.
- После успешных обязательных проверок не расширять и не повторять набор без нового изменения, failure или конкретного незакрытого риска. Проверка активного пути после rollout остаётся отдельным обязательством, когда её требует owner; этот stop rule не отменяет full suite или before/after behavioral smoke для instruction migration.
- Expected TDD red считать запланированным только когда failing check создан до fix и причина падения подтверждена; wrong runner, compile error и unrelated failure ожидаемым red не являются.
- Сохранять regression check для воспроизводимой ошибки в кодовой базе. Проверка должна различать ошибочное и ожидаемое поведение; не ограничиваться утверждением значения, выставленного самой реализацией.

## SHOULD

- Покрывать happy path, граничные условия, невалидные входы и edge cases.
- Сохранять тесты независимыми и детерминированными.
- В отчете указывать, какие команды запускались и что они подтвердили.
- При невозможности получить green обязательного набора сообщать incomplete/blocker с next-best evidence, а не успешную проверку.
- Для обратимых механических правок без изменения поведения не добавлять тесты, зеркалирующие реализацию. Новая проверка должна защищать наблюдаемое поведение или значимый контракт; пропорциональность не отменяет обязательные regression tests при behavior change.

## MAY

- Использовать дополнительные профильные требования по coverage/типам тестов.

## Команды

```powershell
# Универсальные этапы проверки
# 1) characterization / expected red
# 2) targeted tests
# 3) affected build
# 4) все оставшиеся обязательные проверки; full suite по условиям owner выше
```
